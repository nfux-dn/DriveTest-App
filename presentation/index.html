01 DriveNets Testing Today

Pros & Cons of each approach

Each approach solves part of the challenge. None solves it all.

01 · Manual Testing
Pros
  • Flexible — handles any scenario
  • Deep engineer judgment
  • No framework required
Cons
  • Prone to human error
  • Time consuming, repetitive tasks and regressions
  • Lessons learned not enforced
  • Knowledge isn't preserved
02 · AI-Only Testing
Pros
  • Automated analysis
  • Spots subtle anomalies
  • Minimal human intervention — time efficient
Cons
  • Can hallucinate — cannot be trusted
  • No deterministic guarantee
  • Token cost inefficiency
03 · E2E Testing
Pros
  • Automated testing
  • A part of the CI pipeline
  • Existing test development & execution infrastructure
Cons
  • Limited lab resources, setups & connectivity options
  • Automation constrained by existing test setups & code infrastructure
  • Test coverage intentionally limited to keep CI build times manageable
  • Failure detection limited to predefined validation criteria
  • Limited execution visibility reduces confidence in test results
04 · TOD / AOD-Based Testing
Pros
  • Automated testing
  • Execution and results visibility
  • Proven & trusted testing framework
Cons
  • Out of date
  • Lack of ongoing maintenance
  • Limited access to modifying tests
  • Complicated infrastructure for test creation

04 How it works · The heart of the product

Four values, always kept separate

They are shown side by side in the UI — the system never hides a disagreement.

1 · Execution status

Did it run?

COMPLETED SCRIPT_ERROR INFRA_ERROR TIMEOUT

An execution failure is not a product failure.

2 · Test verdict

What the script decided

PASSED FAILED null

null means the test punts the decision to AI.

3 · AI verdict

The reviewer's opinion

PASSED FAILED INCONCLUSIVE

AI reviews every completed test.

4 · Final verdict

Computed by the backend

PASSED FAILED REVIEW_REQUIRED

One deterministic rule — the single source of truth.

07 How it works · Suites & dynamic prerequisites

Declarative suites, forms that build themselves

  • A Suite is a folder in Git: a README, a merged prerequisites.yaml, and independently-evaluated tests.
  • The YAML generates the device form automatically — IPs, interfaces, selects, confirmations, conditional fields.
  • Automatic checks use a fixed registry of handlers — YAML can never run arbitrary commands.
  • A field marked device_role tells the platform to open one session to that host.
# suites/pwhe_shaping/prerequisites.yaml
id: pwhe_shaping
name: PWHE Shaping
tests:
  - max_bandwidth
  - high_priority_queue

sections:
  - id: connectivity
    fields:
      - id: dut_management_ip
        label: DUT Management IP
        type: ip
        required: true
        device_role: dut   # → opens 1 SSH session
08 How it works · Run-owned connections

Tests never touch a host or a credential

The Run — not the test — owns SSH. A Connection Manager opens one persistent session per device and a token-authed broker on localhost.

  • Each subprocess gets only the broker URL, a per-run token, and device roles.
  • Pluggable transport: a simulated DNOS model for offline demos, real SSH (paramiko) for labs.
  • Sessions are opened at run start and closed automatically at run end.
# inside a test — the ExecutionContext SDK
from drivetest import ExecutionContext

ctx = ExecutionContext.from_env()
dut = ctx.device("dut")

dut.run("show interfaces description")
dut.configure(["interfaces", "  ge0", "  !"])
dut.commit()
dut.rollback(1); dut.commit()   # revert
09 How it works · The AI reviewer

An engineering assistant, not a chatbot

Every completed test is reviewed against its evaluation.md. The reviewer reads the session transcript, stdout/stderr and result.json — and returns a strict schema.

Reads (evidence only)

Session transcript · stdout · stderr · result.json · expected behaviour

Guardrails

Never invents data · never overrides a deterministic FAIL · returns INCONCLUSIVE when unsure

Model, prompt version & policy version are stored with every evaluation for reproducibility.

10 Why not one big E2E test

Atomic, evaluated tests beat a monolithic scenario

Pure end-to-end
  • One giant scenario — the first failure hides everything downstream.
  • Infra crash and product bug are indistinguishable.
  • Binary pass/fail — no reasoning, no evidence, no review.
  • Brittle & slow; hard to reproduce a specific failure.
DriveTest
  • Each scenario is an independent test with its own verdict.
  • Execution status is separate from the product verdict.
  • Deterministic + AI review with evidence and confidence.
  • Structured, stored results — reproducible down to the commit.

DriveTest doesn't replace E2E coverage — it orchestrates it as many small, individually-judged units.
