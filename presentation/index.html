01 DriveNets Testing Today

Pros & Cons of each approach

Each approach solves part of the challenge. None solves it all.

01 · Manual Testing
Pros
  • Flexible — handles any scenario
  • Deep engineer judgment
  • No framework required
Cons
  • Prone to human error
  • Time consuming, repetitive tasks and regressions
  • Lessons learned not enforced
  • Knowledge isn't preserved
02 · AI-Only Testing
Pros
  • Automated analysis
  • Spots subtle anomalies
  • Minimal human intervention — time efficient
Cons
  • Can hallucinate — cannot be trusted
  • No deterministic guarantee
  • Token cost inefficiency
03 · E2E Testing
Pros
  • Automated testing
  • A part of the CI pipeline
  • Existing test development & execution infrastructure
Cons
  • Limited lab resources, setups & connectivity options
  • Automation constrained by existing test setups & code infrastructure
  • Test coverage intentionally limited to keep CI build times manageable
  • Failure detection limited to predefined validation criteria
  • Limited execution visibility reduces confidence in test results
04 · TOD / AOD-Based Testing
Pros
  • Automated testing
  • Execution and results visibility
  • Proven & trusted testing framework
Cons
  • Out of date
  • Lack of ongoing maintenance
  • Limited access to modifying tests
  • Complicated infrastructure for test creation

04 How it works · Anatomy of a suite & test
DriveTest-Scripts/
├── suites/
│   └── <suite_id>/
│       ├── prerequisites.yaml   # suite def + device form
│       ├── README.md            # purpose + connectivity
│       └── tests/
│           └── <test_id>/
│               ├── test.py        # REQUIRED · the test
│               ├── evaluation.md  # AI eval instructions
│               └── README.md      # human notes
├── skills/      # SKILL.md (not used by app)
├── framework/   # shared helpers
└── schemas/     # JSON schemas / docs

Two independent layers of truth

Each suite ships a README + prerequisites that define the Environment tab — the required connectivity scheme and devices. Every test carries a script and an evaluation file.

Layer 1 · Deterministic

test.py runs and decides the test status from the exact deterministic values coded in the script.

Layer 2 · AI Review

Session + trace logs are sent with evaluation.md to an AI agent, which decides an AI review status from the logs & expected results only — independent of the script.

Two independent verdicts — the script's own truth plus an outside AI opinion — add another layer of confidence.

07 How this affects our workflow

The question is no longer “Should we automate it?”
— it becomes “How do we automate it?”

  • Every QA engineer owns and develops an automation suite within their domain.
  • Each suite should be designed to maximize test coverage while requiring as few setup and connectivity changes as possible.
  • The workflow shifts from 100% manual testing to ~80% AI-assisted script development & automation, with the remaining 20% for exploratory testing, edge cases and improvisation.
  • Every test that can be automated is added to the suite and documented in the suite’s README.
  • Lessons learned are implemented as a new test immediately — or existing tests are modified accordingly.
  • If a test can’t yet be automated, it’s clearly marked and documented in Jira as a follow-up automation task.
  • After each execution, the QA engineer manually reviews the report and supporting evidence — backing conclusions with clear, traceable evidence rather than automation alone.
Summary

We harness AI where it’s strongest — rapidly writing scripts and identifying anomalies — while automated scripts provide a deterministic layer that compensates for the margin of error in an AI-only approach.

The best of both worlds: AI for speed, flexibility and analysis; automation for consistency, repeatability and validation.

The result is a more token- and time-efficient methodology that cuts manual effort and saves significant testing time in the mid and long term.

AI accelerates the work. Automation + AI insights make it reliable.
08 What’s next

Implementation Paths & Extensions

E2E-compatible format

Python scripts can be written in the E2E format, allowing future merging if/when the E2E environment becomes capable of it.

Bug creation for failed tests

Open a Jira bug in one click from a failed test — pre-filled with the verdict, logs, evidence and commit.

Jira integration
  • A comprehensive execution & log report is auto-generated and attached to the relevant Jira Test Plan.
  • Epic / Jira sync links each automated test to its corresponding Jira test case.
  • Results & status reflect in Jira automatically — less manual reporting, an always-current Test Plan.
Methodology over platform

E2E — or a different platform — could close the gaps and host this methodology. What matters is the shift in testing methodology, not the specific tool.

SSO & access control

Company single sign-on and per-team permissions for enterprise rollout.

Analytics & trends

Graphs that compare previous runs per platform to detect changes in execution time and errors raised over time.
